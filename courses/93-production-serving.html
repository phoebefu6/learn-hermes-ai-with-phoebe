Part 1 · covers the vLLM and SGLang tool-calling docs

The serving landscape ~9 min read

Three lanes, three jobs. Pick the lane before you pick the engine, and most serving decisions make themselves.

Self-studyDev serving vs production serving3 min read▶

Ollama is a superb development tool - and that is a positioning, not an insult. The honest split:

  • Ollama / LM Studio (laptop lane): optimized for one human. Instant model swapping, sane defaults, runs on a Mac. What they do not give you: high-throughput continuous batching across dozens of concurrent requests, first-class tool-call parsing, or multi-GPU tensor parallelism.
  • vLLM / SGLang (server lane): optimized for many humans. Continuous batching keeps the GPU saturated as requests arrive and finish mid-flight; paged attention manages KV-cache memory; tensor parallelism spreads a big model across GPUs. This is what "production" means mechanically.
  • llama.cpp (edge lane): optimized for running ANYWHERE - CPU-only boxes, odd accelerators, small appliances - via aggressive GGUF quantization. Part 2 is all about it.

Rule of thumb: if your users could all be replaced by you pressing Enter, stay on Ollama. The moment real concurrent traffic shows up, move to the server lane - do not try to scale the laptop lane with a load balancer and hope.

Self-studyvLLM and the parser named hermes4 min read▶

Here is the flex hiding in plain sight: to serve Hermes on vLLM with working tool calls, you pass a parser that is literally named after the model family:

★ The flag combovllm serve NousResearch/Hermes-4-14B --enable-auto-tool-choice --tool-call-parser hermes
  • --enable-auto-tool-choice lets the server decide when the model's output is a tool call versus plain text.
  • --tool-call-parser hermes tells vLLM the model emits the Hermes format - <tool_call>{...}</tool_call> blocks, the format you hand-parsed in Session 6. The server now extracts them and returns proper OpenAI-style tool_calls objects.

Why is it named that? Because Hermes 2 Pro's function-calling format was so widely copied that it became the de facto open standard - so when vLLM built parsers, "hermes" was the name for the whole format family. The model you have been learning is not just compatible with the standard; it IS the standard.

Real world

The week-two bug this prevents. Teams serve a tool-calling model without a parser, and their client library sees tool calls as weird text in content. Everything "works" in a smoke test, then the agent loop silently never calls a tool. The parser flag is the difference between text that looks like a tool call and a tool call.

Self-studySGLang and Hermes 4.32 min read▶

SGLang is the other serious server-lane engine - same job as vLLM (continuous batching, OpenAI-compatible API, tensor parallelism), with a particularly strong reputation for structured-output workloads.

  • The 4.3 wrinkle: for Hermes 4.3, SGLang works with the qwen25 tool-call parser rather than a hermes-named one - the tag conventions line up with Qwen 2.5's format handling. Not intuitive; worth writing on a sticky note.
  • Choosing between them: both are production-grade. If your team already runs one, stay on it. If starting fresh with Hermes, vLLM's named parser and larger deployment corpus make it the lower-friction default; benchmark SGLang if structured output dominates your traffic.
Part 2 · covers llama.cpp server docs + the official GGUF repo

llama.cpp everywhere ~8 min read

llama.cpp is the runtime that made local LLMs a thing: a C++ engine that runs GGUF-quantized models on nearly any hardware, with an OpenAI-compatible server built in. Ollama itself is built on it. Going direct buys you control and the smallest possible footprint.

Self-studyThe one-liner, and two gotchas that waste an afternoon4 min read▶

Modern llama.cpp pulls models straight from HuggingFace. One command stands up an OpenAI-compatible server with the official Hermes 4.3 GGUF:

★ The one-linerllama-server -hf NousResearch/Hermes-4.3-36B-GGUF:Q4_K_M --jinja
  • Gotcha 1 - the binary name. Some HuggingFace page snippets render the command as llama serve. That command does not exist: the actual binary is llama-server (hyphen, no subcommand). If your shell says command not found, this is why.
  • Gotcha 2 - the chat template. The --jinja flag tells llama.cpp to use the chat template embedded in the GGUF file. Without it you can get a generic template - and a wrongly templated Hermes will mangle system prompts, think tags, and tool calls in ways that look like a dumb model rather than a config error. From Session 3 you know the template IS the protocol: always pass --jinja.
Seen in the wild - do not copyllama serve -hf NousResearch/Hermes-4.3-36B-GGUF:Q4_K_M
Why go direct instead of Ollama? Control (every server flag exposed), footprint (one static binary, fine for containers and appliances), and currency (new llama.cpp features land here first). The price is that YOU own the flags Ollama was quietly setting for you - context size included.

Nous publishes official GGUFs at NousResearch/Hermes-4.3-36B-GGUF. The ladder, with directional hardware fits (leave a few GB of headroom for the KV cache and the OS):

Part 3 · the config traps

Serving choices that bite ~8 min read

Most serving outages are not crashes - they are configs that were fine in the demo and wrong at scale. Four to get right on day one.

Self-studyContext windows are a per-model fact3 min read▶

"Hermes" is not one context window. Configure per model, and remember the KV cache for long contexts eats GPU memory that then cannot hold concurrent users:

ModelContext windowServing implication
Hermes 4.3 36B512KHuge headroom - but a full 512K request can monopolize a GPU's memory; cap max length per request in prod
Hermes 4 70B / 405B131K classThe standard Llama 3.1 window - plan KV cache accordingly
Hermes 4 14B40,960The small one - reasoning traces can eat most of it (D1 tells that story); budget prompts tightly

Long-context serving is a memory budget negotiation: every token of context a request holds is KV cache another user cannot have. Set max_model_len (vLLM) to what your product actually needs, not to what the model can do.

Self-studyFP8 - the first lever for big models2 min read▶

Official FP8 variants exist for Hermes 4 70B and 405B - and for server-lane deployments of the big models, FP8 is usually the first lever to pull:

  • Roughly half the memory of BF16 weights, with minimal quality loss on GPUs that support it natively (Hopper/Blackwell class).
  • Halving weights buys concurrency: the memory you free becomes KV cache, which becomes more simultaneous users on the same hardware.
  • Order of operations: BF16 does not fit? Try FP8 before reaching for aggressive integer quants - it usually costs less quality per GB saved, and vLLM/SGLang serve it natively.
Self-studySampling defaults live in the server now2 min read▶

On your laptop, you set temperature per chat. In production, defaults belong in the serving layer so every client gets known-good behavior. The official Hermes recommendation:

★ Official sampling defaultstemperature 0.6, top_p 0.95, top_k 20
  • Set these as server-side defaults; let clients override deliberately, not accidentally.
  • Engine defaults differ (some ship temperature 1.0) - an unset temperature is a silent quality bug that shows up as "the model got flaky in prod".
Self-studyCapacity planning - directional numbers3 min read▶

Real capacity depends on your traffic shape (prompt length, output length, burstiness), so treat this as a starting sketch, not a promise:

Concurrent users (chat-like)Directional setup
1-5One 24GB GPU · 14B class, or 36B quantized via llama.cpp
10-50One 80GB GPU · vLLM/SGLang · 14B-36B, continuous batching doing the heavy lifting
50-2002-4 x 80GB · tensor parallelism · 70B FP8 becomes realistic
MoreMultiple replicas behind a load balancer · benchmark before you buy
  • The one rule that survives contact with reality: Ollama is a dev tool - for concurrent production traffic use vLLM or SGLang with tensor parallelism, and load-test with YOUR prompt/output length distribution before committing to hardware.
Real world

The demo-day trap. A team demos on Ollama, gets budget, ships the same box to 40 users. Requests queue serially, p95 latency hits minutes, and the postmortem says "the model is too slow". The model was fine - the lane was wrong. Continuous batching on vLLM turned the same GPU into a service.

Build-along

Stand up a real endpoint ★ ~15 min · GPU box or cloud instance

Full circle with the course spine: stand up a production-grade Hermes endpoint, then point your Session 5 script at it - same OpenAI client, one changed line.

On a machine with an NVIDIA GPU (a rented cloud instance is fine), install vLLM into a fresh environment: pip install vllm.

Serve Hermes with tool-call parsing on - the Part 1 flag combo. First run downloads the weights from HuggingFace, so give it time.

Smoke-test from a second terminal with the curl below. You should get an OpenAI-shaped JSON response back - that shape is the whole point.

Now open your Session 5 structured-output script and change ONE line: base_url="http://localhost:8000/v1" (from your Ollama localhost:11434/v1). Run it. Same client, same schema prompt, production engine.

If you built the Session 6 tool loop: run it against the new endpoint and notice tool calls now arrive as parsed tool_calls objects, not text you regex out. That is --tool-call-parser hermes earning its keep.

★ The serve commandvllm serve NousResearch/Hermes-4-14B --enable-auto-tool-choice --tool-call-parser hermes
★ The curl smoke testcurl http://localhost:8000/v1/chat/completions -H "Content-Type: application/json" -d '{"model": "NousResearch/Hermes-4-14B", "messages": [{"role": "user", "content": "One sentence: who are you?"}], "temperature": 0.6, "top_p": 0.95}'
No GPU handy? Do the same exercise in the edge lane: the llama-server one-liner from Part 2 also exposes an OpenAI-compatible API (default port 8080). Slower, but the client-side lesson - one base_url swap, everything else unchanged - lands identically.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · What do the flags --enable-auto-tool-choice --tool-call-parser hermes give you on vLLM?

Without the parser, tool calls arrive as text in content and agent loops silently break. The parser is named hermes because the Hermes function-calling format became the open standard vLLM parses.

2 · Your shell says "command not found" after copying a llama.cpp command from a HuggingFace page. Most likely fix?

Some HF page snippets misrender the command. The real invocation is llama-server -hf NousResearch/Hermes-4.3-36B-GGUF:Q4_K_M --jinja - and skipping --jinja risks a wrong chat template, which breaks system prompts, think tags, and tool calls.

3 · Your Ollama demo wowed everyone, and now 40 users are coming Monday. What is the right move?

Ollama is a dev tool built for one user at a time. Concurrent production traffic is what vLLM/SGLang exist for: continuous batching keeps the GPU saturated across in-flight requests, which is the difference between a queue and a service.
