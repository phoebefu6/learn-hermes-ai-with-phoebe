Part 0

The session where your assistant becomes software

For four sessions your assistant has been talking TO you. Useful, but a paragraph of prose is a dead end for automation - no script can reliably read "Sure! The contact's name appears to be Dana...". Today we make Hermes answer in a machine-readable contract: JSON that matches a schema you define. That one change turns every conversation into a pipeline stage - extraction, classification, routing, logging - anything downstream code can consume. This is the skill that separates "I chat with a local model" from "I build with one".

Part 1 · covers the model cards' JSON mode + Hermes-Function-Calling repo

From prose to contract 8 min live

The move is simple: instead of asking for an answer, you hand the model a contract - a JSON schema - and Hermes was explicitly trained to honor it. One system prompt is all it takes.

LiveWhy free text breaks pipelines3 min▶

Ask a model to "list the contact details" and you get prose. Prose is a moving target:

  • Format drift. Today it answers with bullets, tomorrow with a sentence, Thursday it adds "Certainly! Here are the details:". Your regex dies on Thursday.
  • Missing fields go silent. No phone number in the text? Prose just... omits it. Your downstream code never learns the field was expected.
  • No types. Is "confidence: high" a string, an enum, or a number? Prose does not say. Your database cares.

A schema kills all three problems at once: fixed keys, declared types, explicit required fields. And the failure mode changes from "silent garbage flows downstream" to "validation error at the door" - which is exactly where you want failures to happen.

Real world

The inbox miner. A freelance recruiter gets 40 candidate emails a day, each formatted differently. Her old workflow: copy-paste into a spreadsheet, 45 minutes. Her new one: a local Hermes with a Candidate schema turns each email into a validated row - name, role, years, salary expectation - and a script appends it to the sheet. Same laptop, zero cloud, 3 minutes.

LiveThe schema system prompt - one prompt, trained in3 min▶

This is the canonical JSON-mode prompt from the Hermes model cards. Not folklore, not a community hack - it is the exact scaffolding the model was trained on. Use it verbatim and substitute your schema where {schema} is:

★ The canonical schema prompt (from the Hermes 3/4 model cards)You are a helpful assistant that answers in JSON. Here's the json schema you must adhere to: <schema> {schema} </schema>

Hermes replies with a JSON object that conforms to the schema - no preamble, no "Here is your JSON:", no markdown fences to strip. Two things make this stronger than "please answer in JSON" folk prompting:

  • It is a trained behavior, not a request. Hermes was explicitly post-trained to produce schema-conformant JSON for a given schema - the prompt above is the key that unlocks it.
  • It also repairs. The same training taught Hermes to take a malformed JSON object and fix it to conform - Demo 2 exploits this deliberately.
Self-studyHow schema adherence was trained - Pydantic rejection sampling2 min read▶

Why does this work so reliably? Because of how the training data was built. Per the Hermes 4 technical report (section 2.2.4), the JSON-mode training examples were generated and then validated with Pydantic before being kept: candidate outputs that failed schema validation were rejected, and only conformant ones made it into the training set. That is rejection sampling with a real validator as the judge - the model literally never saw a "correct" example that did not parse.

The practical consequence for you: the tool you use to CHECK the output (Pydantic) is the same family of tool that CURATED the training data. You are validating with the judge it was raised on. The reference implementation lives in the official Hermes-Function-Calling repo - see jsonmode.py for the exact pattern we build in Demo 1.

The validation loop 7 min live

"The model usually returns valid JSON" is a demo. "My code verifies every response and recovers when it fails" is software. The loop below is the difference, and it is about ten lines of Python.

LivePydantic drives the whole loop3 min▶

One Pydantic class plays four roles in this pipeline, which is why the pattern is so compact:

  • Definition: your Python class IS the contract - fields, types, optionals, defaults.
  • Schema: Model.model_json_schema() dumps the JSON schema you paste into the system prompt. Never hand-write schemas.
  • Validation: Model.model_validate_json(reply) parses AND type-checks in one call. If it returns, you hold a real typed object.
  • Error report: when it raises, the ValidationError message says exactly which field failed and why - which is precisely what you feed back to the model on retry.

So the loop is: build prompt from the class, generate, validate against the class, and on failure send the error text back for one repair round. Define once, use four ways.

LiveJSON repair - the trained fallback2 min▶

Here is the underrated half of the JSON-mode training: Hermes was also taught to repair malformed JSON. Hand it a broken object - trailing comma, unquoted key, a stray single quote - together with the schema, and it returns the corrected, conformant version.

That gives your retry branch real teeth. Instead of regenerating from scratch (slow, may fail differently), you paste the broken output plus the validation error and ask for a fix. In practice the repair round almost always lands, because fixing syntax is an easier task than the original extraction. Demo 2 does this live with deliberately vandalized JSON.

Repair is a safety net, not a license If more than a few percent of your calls need repair, something upstream is wrong - usually temperature too high or a schema with ambiguous field names. Fix the cause; keep the net.
Self-studyTemperature discipline for structured output2 min read▶

The official Hermes sampling recommendation (temperature 0.6, top_p 0.95, top_k 20) is tuned for conversation, where variety is a feature. Extraction is the opposite job: there is one right answer hiding in the text, and creativity is pure risk.

JobTemperatureWhy
Chat, brainstorming, personas0.6 (official default)Variety and voice are the point
Extraction, classification, JSON0.1-0.3Deterministic-ish output, fewer format surprises
Repair round0.0-0.1Syntax fixing wants zero adventure

Habit to build: set temperature per CALL, not per model. Your assistant chats at 0.6 and extracts at 0.2 within the same session - the API makes this a one-word argument.

Extract records from messy text ★ 10 min · build your own

The full pipeline in ~25 lines: Pydantic model, schema dump, canonical prompt, local Ollama call, validation. This exact script is the seed of every extraction tool you will ever build with Hermes.

Prereqs check: Ollama running with your hero model pulled (Session 2), plus pip install openai pydantic. The openai library talks to Ollama because Ollama exposes an OpenAI-compatible endpoint at http://localhost:11434/v1 - the api key is literally the string "ollama" (anything works).

Write a Pydantic model for a contact record: name, company, email, optional phone. This class is your schema, validator, and typed result all at once.

Dump the schema with Contact.model_json_schema() and drop it into the canonical <schema> system prompt from Part 1 - verbatim, substitution only.

Run the script below against a genuinely messy sentence. Note the temperature: 0.2, because this is extraction, not conversation.

Validate with Contact.model_validate_json(...). When it prints a typed object, pause on what just happened: unstructured text went in, a contract-compliant record came out, and nothing left your machine.

Stress it: remove the phone number from the text (optional field should come back null), then add a second person (watch what a single-object schema does - and why lists need a wrapper model).

★ extract.py - the whole pipeline, ~25 linesimport json from openai import OpenAI from pydantic import BaseModel class Contact(BaseModel): name: str company: str email: str phone: str | None = None schema = json.dumps(Contact.model_json_schema(), indent=2) SYSTEM = ( "You are a helpful assistant that answers in JSON. " "Here's the json schema you must adhere to:\n" f"<schema>\n{schema}\n</schema>" ) client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama") messy = ("Met Dana Reyes at the logistics expo - she heads data at " "Brightleaf Logistics, said to email dana.reyes@brightleaf.example, " "mobile is 555-0142 but she prefers email.") resp = client.chat.completions.create( model="hf.co/bartowski/NousResearch_Hermes-4-14B-GGUF:Q4_K_M", temperature=0.2, messages=[{"role": "system", "content": SYSTEM}, {"role": "user", "content": messy}], ) contact = Contact.model_validate_json(resp.choices[0].message.content) print(contact)
On the on-ramp model? Swap the model line for hermes3:8b - the schema prompt is trained into Hermes 3 as well. The 14B is just noticeably steadier on gnarly schemas.

The repair shop + your assistant learns JSON ★ 8 min · upgrade the project

Two quick wins: watch Hermes fix JSON you deliberately broke, then give your running-project assistant a structured voice - every reply from now on is a parseable object.

Vandalize some JSON. Take Demo 1's output and break it two ways: add a trailing comma, un-quote a key. This is exactly the kind of damage real-world feeds and older models produce.

Send it to Hermes with the schema prompt plus one line: "The following JSON is malformed. Repair it so it is valid and conforms to the schema. Return only the corrected JSON." Paste the broken object as the user message.

Validate the repaired reply with model_validate_json. It passes - repair-to-schema is a trained behavior, not luck. This is your retry branch from Part 2, live.

Now the project upgrade: give your assistant the structured-reply system prompt below, so every answer arrives as {intent, answer, confidence}.

Chat normally for three or four turns. Every reply is now a parseable object: intent tells your code what kind of request it was, answer carries the text, confidence lets you route low-confidence replies to a human. Your assistant just grew an API.

The vandalized JSON - feed this to the repair shop{"name": "Dana Reyes", company: "Brightleaf Logistics", "email": "dana.reyes@brightleaf.example", "phone": "555-0142",}
★ The assistant upgrade - structured-reply system promptYou are my private assistant. You are a helpful assistant that answers in JSON. Here's the json schema you must adhere to: <schema> {"type": "object", "properties": {"intent": {"type": "string"}, "answer": {"type": "string"}, "confidence": {"type": "number", "minimum": 0, "maximum": 1}}, "required": ["intent", "answer", "confidence"]} </schema>
Real world

The triage bot. A two-person consultancy pipes inbound inquiry emails through a local Hermes wearing exactly this {intent, answer, confidence} prompt. High-confidence "pricing question" intents get an auto-drafted reply for review; anything below 0.7 confidence lands in a human queue untouched. No cloud, no per-call fees, and the schema is the whole integration.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · Why does the <schema> system prompt work so reliably on Hermes?

It is a trained behavior: JSON-mode training data was kept only if it passed Pydantic validation (Hermes 4 report §2.2.4). You are validating with the judge the model was raised on.

2 · You are extracting records, not chatting. What do you do with temperature?

0.6 is tuned for conversation. Structured output wants near-deterministic sampling; set temperature per call, and go even lower (0.0-0.1) for repair rounds.

3 · The reply fails model_validate_json. Best first move?

Repair-to-schema is a trained Hermes behavior and syntax fixing is an easier task than the original extraction. Cap retries at 2, then flag for a human.
