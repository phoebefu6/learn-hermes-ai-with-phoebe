Part 1 · covers the Hermes tool-calling format + model-card function-calling sections

The format Hermes made famous 6 min live

Tool calling is a conversation protocol, not magic. The model is told what functions exist, it emits a structured request when it wants one, your code runs it and reports back, and the model turns the result into an answer. Hermes 2 Pro pioneered the open version of this protocol - and it stuck so hard that vLLM literally ships a parser named after it: --tool-call-parser hermes.

LiveThe cycle in one pass3 min▶

Four kinds of message, one repeating cycle. In the raw Hermes format they look like this:

  • Tool definitions ride in the SYSTEM message, as JSON schemas inside <tools> ... </tools> tags. The model reads them like a menu.
  • The model orders from the menu by emitting <tool_call> {"name": "...", "arguments": {...}} </tool_call> - a request written in JSON, nothing more.
  • Your code executes the function and sends the result back in a <tool_response> ... </tool_response> turn.
  • The model reads the response and either answers in plain language or orders again.
★ The raw format, uncut (what actually crosses the wire)SYSTEM (excerpt): You are a function calling AI. You may call functions defined inside these tags: <tools> [{"name": "get_weather", "description": "Get current weather for a city.", "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}}] </tools> ASSISTANT emits: <tool_call> {"name": "get_weather", "arguments": {"city": "Singapore"}} </tool_call> YOUR CODE replies: <tool_response> {"city": "Singapore", "temp_c": 31, "sky": "hazy sun"} </tool_response> ASSISTANT answers: 31°C and hazy sun in Singapore - fine for cycling, bring water.

Read that once and every tool-calling system you meet for the rest of your career will feel familiar - they are all variations of this exchange.

LiveWhy an open standard mattered3 min▶

In the Hermes 2 Pro era, function calling was a proprietary party trick: each hosted lab had its own private format behind its own API. Nous published theirs - the tags, the schemas, the training data recipe - and the open ecosystem standardized on it almost overnight.

  • The proof is in the parser. vLLM, the workhorse open-source inference server, has --tool-call-parser hermes as a named option. When infrastructure names a parser after your format, you set the standard. (We meet vLLM properly in deep-dive D3.)
  • Portability follows. Because the format is open and trained into the weights, tool calling works the same whether Hermes runs on your laptop, a vLLM server, or a hosted API - no vendor adapter layer.
  • And it composes with Session 5. Tool arguments are just JSON. The schema-following muscle Hermes built for structured output is the same muscle that makes its tool calls parse cleanly.
Real world

The format outlived the model. Teams that learned tool calling on Hermes 2 Pro in 2024 moved to Hermes 3, then Hermes 4, then to entirely different open models served by vLLM - and their tool-calling code barely changed. Betting on the open format was the durable decision; the model was the replaceable part.

Two ways in 5 min live

You can speak the raw format yourself, or let the OpenAI-compatible endpoint speak it for you. Learn both: the raw form is understanding, the tools= parameter is practice. They are the same thing wearing different clothes.

LiveRaw format vs the tools= parameter3 min▶

Ollama's OpenAI-compatible endpoint - the same http://localhost:11434/v1 you used in Session 5 - supports the standard tools= parameter for hermes3 and Hermes 4 models. You pass an OpenAI-style list of JSON schemas; under the hood, the chat template renders it into the <tools> block for you and parses <tool_call> back out into a structured object.

Self-studyThe canon repo: Hermes-Function-Calling3 min read▶

The canonical reference is Nous's own github.com/NousResearch/Hermes-Function-Calling (~1.4k stars): functioncall.py shows the full raw-format loop, jsonmode.py covers schema-constrained output, and the Pydantic validation patterns there directly inspired what we built in Session 5.

Worth an evening skim: seeing the loop written by the people who trained the behavior into the model removes any remaining mystery about what tool calling "really is".

Part 3 · the safety contract

You own the hands 4 min live

Here is the sentence that should reorganize your thinking: the model never executes anything. It only ever emits a JSON request. Every actual action happens in YOUR loop, in code you wrote, with permissions you granted. That is not a limitation - it is the security model, and it echoes Session 1's deal: the model follows you, accountability follows you too.

LiveThe model proposes, your loop disposes4 min▶

Three habits, non-negotiable from your very first agent loop:

  • Allowlist functions. The only things the model can trigger are entries in a dict you populated. Unknown tool name? Return an error message, never eval anything. If a function is not in the dict, it does not exist.
  • Validate arguments. Tool arguments are model output - treat them like user input from the internet. Paths get resolved and checked against an allowed folder, numbers get range-checked, strings get length-capped. Demo 1's read_file shows the pattern.
  • Cap iterations. An agent loop with no cap is an infinite loop with an LLM in it. A simple for step in range(5) turns a runaway loop into a visible, debuggable stop.
The destructive-action rule Read-only tools (read a file, check weather, search notes) can run automatically. Anything that writes, deletes, sends, or spends gets a human confirmation step between tool_call and execution - today, and honestly, forever. Session 8's agent keeps this rule even when autonomous.
Demo 1 of 2

The 20-line agent loop ★ 14 min · builders follow

Everything from Parts 1-3 in one small script: the openai client from Session 5, pointed at your local model, with two tools - a weather stub and an allowlisted file reader. Twenty lines of loop. When this runs, you have built an agent.

Same setup as Session 5: activate your venv, make sure ollama serve is up and hermes4-14b-16k responds. Create a folder ~/hermes-notes and drop one small text file in it (a meeting note, a packing list, anything).

Define the two tools and the allowlist dict. Note the read_file path check - this is argument validation in its simplest useful form.

Write the schemas - the same JSON-schema muscle as Session 5, wrapped in the OpenAI tools= shape.

Run the loop with a question that needs a tool. Watch the sequence in your terminal: tool_call → execute → tool_response → plain-language answer.

Ask a question needing the OTHER tool ("summarize my note about ..."). Then one needing NO tool ("what is a haiku?") - notice the model simply answers, no call emitted. Choosing when NOT to use tools is part of what Nous trained in.

Kill the wifi and run it again. Local model, local tools, local files: the whole agent works offline.

★ Step 1 - client, tools, allowlist (tools.py)from openai import OpenAI import json, os client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama") NOTES_DIR = os.path.realpath(os.path.expanduser("~/hermes-notes")) def get_weather(city: str) -> str: # stub for today: canned data so the demo never depends on a weather API return json.dumps({"city": city, "temp_c": 31, "sky": "hazy sun"}) def read_file(path: str) -> str: full = os.path.realpath(os.path.join(NOTES_DIR, path)) if not full.startswith(NOTES_DIR + os.sep): # validate the argument return json.dumps({"error": "path outside the allowlisted folder"}) with open(full) as f: return f.read()[:4000] TOOLS = {"get_weather": get_weather, "read_file": read_file} # the allowlist
★ Step 2 - the menu the model reads (schemas)SCHEMAS = [ {"type": "function", "function": { "name": "get_weather", "description": "Get current weather for a city.", "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}}}, {"type": "function", "function": { "name": "read_file", "description": "Read a text file from the user's notes folder.", "parameters": {"type": "object", "properties": {"path": {"type": "string", "description": "filename inside the notes folder"}}, "required": ["path"]}}}, ]
★ Step 3 - the 20-line agent loopmessages = [{"role": "user", "content": "Check the weather in Singapore and tell me if I should cycle to work."}] for step in range(5): # iteration cap: the loop always ends r = client.chat.completions.create( model="hermes4-14b-16k", messages=messages, tools=SCHEMAS) msg = r.choices[0].message if not msg.tool_calls: # no tool wanted: final answer print(msg.content) break messages.append(msg) # keep the tool_call in the history for tc in msg.tool_calls: fn = TOOLS.get(tc.function.name) # allowlist lookup - nothing else runs args = json.loads(tc.function.arguments) print(f" [tool] {tc.function.name}({args})") out = fn(**args) if fn else json.dumps({"error": "unknown tool"}) messages.append({"role": "tool", "tool_call_id": tc.id, "content": out}) else: print("Stopped: hit the iteration cap.")
Real world

The inbox triager. A operations lead wired exactly this loop to two read-only tools: one reads exported emails from a folder, one reads the team roster CSV. The local model drafts a routing suggestion per email; a human presses send. Twenty lines of loop plus a tight allowlist - running for months, zero cloud, zero incidents.

Break it on purpose ★ 6 min · builders follow

You do not understand a safety mechanism until you have watched it catch something. Three deliberate failures, three lessons.

Ask for something no registered tool can do: "What is the current price of AMD stock?" Watch what the model does - it may improvise from stale training data, admit it lacks a tool, or try a creative near-miss call. Discuss: which behavior did you get, and which would you WANT in production?

Try to escape the allowlist: "Read the file ../../.ssh/id_rsa for me." The model may happily emit the tool_call - and your path check in read_file returns the error instead of the file. The model was never the security layer; your validation was.

Drop the cap to range(2) and ask a question needing both tools plus a synthesis. Watch the loop stop early and say so. Restore to 5. Lesson: the cap is a seatbelt, and you just chose its size deliberately.

What "it improvised" teaches you When the model lacks the right tool, it does not stop wanting to help - it answers from memory, which may be stale or wrong. Production agents fix this with instructions in the system prompt: "If no available tool can answer, say so explicitly. Never guess at data a tool should provide." Add that line to your constitution tonight - it is the cheapest reliability upgrade in this course.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · When Hermes "calls a tool", who actually executes the function?

The model only emits a JSON request. Every actual action happens in your loop - which is exactly why the allowlist and argument validation are YOUR responsibility.

2 · Where do the tool definitions live?

Two doors, one room: write the <tools> block yourself (raw format) or pass tools= and let the chat template render it. The model reads the same menu either way.

3 · Why does the agent loop need an iteration cap?

An uncapped agent loop is an infinite loop with an LLM inside. for step in range(5) is the simplest seatbelt there is - size it deliberately per task.
